## Local projects

A selected Project is the working boundary for TL Studio. Files, Editor tabs, Search, Terminal commands, Preview, Sessions, Changes, Agent context, Permission requests, and Questions all follow the active project.

Switching projects clears pending composer attachments. If you have unsaved editor changes, TL Studio asks before discarding that work during a project switch.

## Sessions

TL Studio presents and manages coding sessions while Agent execution remains behind the local runtime contract. You can create, rename, delete, reopen, and inspect sessions from the workspace.

Starting a new session clears unsent attachments. Attachments that were already sent remain represented on their message in conversation history.

A read-only compatibility bridge can open older alpha-era sessions that used an earlier protocol. Those legacy histories are project-scoped and are not mutated through the compatibility path.

## Messages and live activity

TL Studio follows session state and live events rather than treating the first HTTP response as the final answer. The interface can render assistant text, Reasoning, Tools, file activity, Permission requests, Questions, and attachments as a task progresses.

## Usage summaries

Where execution data is available, TL Studio shows per-turn and project-level totals such as tokens, requests, elapsed time, Reasoning, and cache usage. These are local workspace summaries, not telemetry uploaded to a TL Studio service.
