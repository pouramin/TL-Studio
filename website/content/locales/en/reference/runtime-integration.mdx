TL Studio keeps implementation-specific engine details behind a local adapter. The current bundled implementation is **Kilo Code 7.6.2**. Normal users do not need to install, configure, or operate that engine separately.

## Public local contract

Browser modules use TL Studio-owned routes:

- `/local/*` for project files, Search, process/Terminal, and Preview;
- `/runtime/*` for Agent/session execution and runtime-facing product concepts.

The launcher strips/translates the runtime prefix, injects local authentication, and supplies the selected Project context. Browser code never needs the engine password.

## Browser adapter

Runtime calls are centralized in `cmd/launcher/ui/runtime-api.ts` and its compiled browser output. Other UI modules should not construct implementation-specific engine routes.

CI explicitly checks this boundary so product-facing JavaScript cannot drift back toward vendor-specific endpoint names or account wording.

## Provider/model boundary

Provider and Model definitions are now TL Studio-owned and stored in TL Studio's local registry. The launcher translates them into the current engine's configuration internally.

Credentials, Agent/session execution, Tools, Permissions, Questions, and Model inference still depend on the bundled engine in v0.2.

## Advanced override

Maintainers can point TL Studio at a compatible runtime binary with:

```bash
tl-studio --runtime-bin /path/to/runtime
```

## Upgrade rule

Before changing the bundled engine, compatibility checks must cover Project routing, Agent/Provider/Session shapes, Messages, Permissions/Questions, Events, Provider configuration, and a real file-write Tool flow.
