TL Studio v0.2 separates **product capabilities owned by TL Studio** from Agent execution performed behind a generic runtime contract.

```text
Browser IDE
  │
  ├─ /local/* ───────► TL Studio local core
  │                    ├─ Project filesystem
  │                    ├─ Editor state
  │                    ├─ Project Search
  │                    ├─ Process / Terminal
  │                    └─ Live Preview control
  │
  └─ /runtime/* ─────► TL Studio runtime contract
                        ↓
                    Runtime adapter
                        ↓
                    Bundled Agent engine
                        ├─ Sessions / Agent execution
                        ├─ Tools / Permissions / Questions
                        ├─ Provider credentials
                        └─ Model inference

Live Preview
  └──────────────────► separate loopback origin
```

## TL Studio owns

- the standalone Browser IDE and Agent workspace;
- local launch and lifecycle;
- Project selection;
- writable Project Files and multi-tab editor;
- revision/conflict protection and external-change reconciliation;
- Project Search;
- local process management and Terminal UX;
- Live Preview control and static preview server;
- Provider and Model definitions;
- the `/local/*` project-tool API;
- the product-facing `/runtime/*` contract;
- recovery UX, local security, packaging, releases, and branding.

## Engine responsibilities that remain

The bundled Agent engine still handles Agent/session execution, Tool execution, Permission/Question internals, Provider credential persistence, and Model inference.

That boundary is intentionally hidden from normal user workflows. Browser modules depend on TL Studio concepts and generic routes rather than implementation-specific endpoint names.

## Provider and Model ownership

Custom Provider definitions are stored in TL Studio's own versioned local `providers.json`. TL Studio is the source of truth for Provider ID/name, protocol, Base URL, Model definitions, capability flags, and optional context/output limits.

The launcher translates those definitions to the current Agent engine internally. API keys remain outside the TL Studio registry and are delegated to the engine's local credential store in v0.2.

## Filesystem trust boundary

The Go launcher is the authority for browser filesystem operations. Paths are resolved against the selected Project; traversal, symlink escapes, root mutation, and protected Git metadata mutations are rejected.

Normal saves use a SHA-256 revision token. If disk content changed after a file was read, TL Studio returns a conflict instead of silently overwriting the new version.

## Search and process boundary

Project Search is implemented by TL Studio itself and does not shell out to an external search command.

Terminal commands run through a TL Studio-owned process manager with the active Project as CWD. The current Terminal is a command runner, not a full PTY.

## Preview isolation

Static Project code and Node dev servers are previewed on a **different loopback origin** from TL Studio's control server. Only loopback Preview URLs are accepted.

## Runtime abstraction

The browser talks to `/runtime/*`; the launcher/runtime adapter is responsible for translating that contract to the bundled engine.

The goal is replaceability: new product features should depend on Sessions, Messages, Providers, Models, Permissions, Questions, Tools, and Events as TL Studio concepts rather than on the name or API layout of one engine.
