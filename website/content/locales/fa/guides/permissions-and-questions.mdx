Coding Agent ممکن است قبل از انجام یک عملیات حساس نیاز به Permission داشته باشد یا برای ادامه کار از شما Question بپرسد.

## تصمیم‌های Permission

TL Studio براساس خود Request گزینه‌های قابل استفاده را نشان می‌دهد:

- **Reject** — درخواست را رد می‌کند؛
- **Allow once** — فقط همان Request را تأیید می‌کند؛
- **Always allow these** — اگر Runtime Ruleهای قابل‌استفاده برای Requestهای مشابه بدهد و ذخیره‌کردن Approval امن باشد، آن Ruleها را برای دفعات بعد نگه می‌دارد.

برای Permissionهای حساس مثل skill-shell یا sandbox-escalation، TL Studio عمداً گزینه Persistent **Always allow** را نشان نمی‌دهد. این Requestها با **Allow** نمایش داده می‌شوند و هر بار به تصمیم صریح کاربر نیاز دارند. اگر Runtime هم Persistent Approval را Disable کرده باشد یا Rule قابل‌استفاده‌ای ندهد، گزینه Always نمایش داده نمی‌شود.

هر Approval که از Dialog خود TL Studio انجام می‌دهید به Runtime پین‌شده به‌عنوان پاسخ Human و Interactive فرستاده می‌شود. این نکته مهم است چون Runtime فعلی برای Permissionهای حساس به `interactive: true` نیاز دارد و Approval غیرInteractive را عمداً نادیده می‌گیرد.

قبل از Allow کردن Command، File Change یا Tool Behavior حساس، Action، Patternها و Metadata درخواست را بخوانید.

## Development Preview: Permission Policy خود TL Studio

در Stable v0.2.1، رفتار Remembered Approval هنوز به Ruleهای قابل‌استفاده‌ای وابسته است که Runtime ارائه می‌کند.

در Preview خصوصی **v0.3.0-alpha.7**، Persistence به خود TL Studio منتقل شده است. Launcher Routeهای `/local/permissions*` را مالک است و Ruleهای Remembered از نوع **allow** را داخل فایل Local به نام `permissions.json` و در Scope همان Project ذخیره می‌کند.

Policy در Preview عمداً محافظه‌کار است:

- فقط Matcher Tokenهای canonical که Runtime می‌دهد ذخیره می‌شوند و TL Studio Wildcard گسترده‌تر اختراع نمی‌کند؛
- برای Auto Approval باید همه Matcherهای Request آینده از قبل پوشش داده شده باشند؛
- Requestهای حساس `skillShell` و `sandboxEscalation` هیچ‌وقت Remember یا Auto-approve نمی‌شوند؛
- Request دارای `disableAlways` همیشه Interactive می‌ماند؛
- Ruleهای ذخیره‌شده در Settings دیده می‌شوند و می‌توان آن‌ها را Forget کرد؛
- کلیک صریح User به‌صورت Interactive Approval فرستاده می‌شود، اما Rule ذخیره‌شده به یک One-time Approval غیرInteractive تبدیل می‌شود.

خود Runtime همچنان Permission Request را در مرز Tool تولید و نتیجه نهایی را Enforce می‌کند؛ Persistence و Decision Policy متعلق به TL Studio می‌شود.

## Questionها

Questionهای تعاملی را می‌توانید مستقیم داخل TL Studio پاسخ دهید. بسته به Request، UI می‌تواند Single Select، Multi Select، Default Option و Custom Answer نشان دهد.

قبل از ادامه باید برای تمام Question Blockها پاسخ انتخاب شود؛ در غیر این صورت می‌توانید کل Question Request را Reject کنید.

Loopback-only بودن سطح Network را محدود می‌کند، اما امنیت نهایی همچنان به Permissionهایی بستگی دارد که به Agent می‌دهید.
