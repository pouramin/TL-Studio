در Stable v0.3، Product-facing Permission Policy و Question Contract متعلق به TL Studio هستند، درحالی‌که Enforcement نهایی در Execution Boundary انجام می‌شود.

## Permission Decision

Request می‌تواند این گزینه‌ها را داشته باشد:

- **Reject** برای رد Action؛
- **Allow once** فقط برای همان Request؛
- **Always allow these** برای Remember کردن Matcher دقیق، فقط وقتی Persistence امن باشد.

Remembered Allow Ruleها داخل فایل Local زیر ذخیره می‌شوند:

```text
permissions.json
```

این Ruleها به Project انتخاب‌شده Scope می‌شوند.

## Ruleهای محافظه‌کارانه

TL Studio برای Permission، Wildcard گسترده اختراع نمی‌کند.

در Compatibility Request فقط Matcher Tokenهای canonical ارائه‌شده توسط Runtime ذخیره می‌شوند و برای Auto Approval باید همه Matcherهای Request بعدی از قبل پوشش داده شده باشند.

در Native Tool Path، Write/Edit می‌تواند Matcher Project-scoped قابل Remember داشته باشد. Tool دارای Execute یا Network حساس در نظر گرفته می‌شود و Remember نمی‌شود.

Classهای حساس Compatibility مثل `skillShell` و `sandboxEscalation` و همچنین Request دارای `disableAlways` همیشه Interactive باقی می‌مانند.

Ruleهای Remembered در Settings دیده می‌شوند و قابل Forget هستند.

## Permission برای Native Tool

Tool فقط‌خواندنی که قابلیت Write/Execute/Network ندارد می‌تواند بدون Prompt اجرا شود.

Write/Edit و Command Execution قبل از اجرای Tool Executor از Native Permission Authorizer خود TL Studio عبور می‌کنند.

Tool ناشناخته در Native Path قابل Authorize نیست.

## Questionها

Questionهای تعاملی از Routeهای متعلق به TL Studio استفاده می‌کنند:

```text
GET  /local/questions
POST /local/questions/{requestID}/reply
POST /local/questions/{requestID}/reject
```

UI می‌تواند Option List، Single/Multi Select، Default و Custom Answer را نمایش دهد. قبل از Forward کردن پاسخ، TL Studio بررسی می‌کند که Request هنوز برای همان Session فعال باشد.

## مسئولیت User

Loopback بودن Network Surface را محدود می‌کند، اما Allow کردن Command یا Write همچنان دسترسی واقعی روی سیستم می‌دهد. قبل از Approval، Action، Pattern و Metadata درخواست را بررسی کنید.
